# Judge Q&A / Defense

Direct answers to the questions this project must survive. Where a number is
cited, it comes from a file in this repo you can re-open and re-run.

---

### "Where did the data come from?"

Nowhere real. There is no SAIL data, no licensed freight index, no live AIS
in this repository. Every dataset is generated by
`data/synthetic/generate_data.py` (deterministic, `seed=42`) and tagged
`ESTIMATED` (a real port/vessel-class with general-knowledge, non-official
dimensions) or `SYNTHETIC` (no real-world source, statistically generated so
the ML pipeline has something realistic to learn from). Full breakdown:
`data/DATA_DICTIONARY.md`. The running app's **Data / Model** page shows
the same disclosure live, and every numeric panel carries a provenance
badge. We would rather show honest synthetic data clearly labelled than
pretend a demo number is a real SAIL contract rate.

### "What is the ML model actually doing?"

`ml/training/train.py` trains a regression model to predict next week's
freight rate ($/tonne) for one origin-cargo lane from lag features (1/2/4/8
week), rolling mean/std, calendar seasonality, and a bunker-price proxy.
Multi-week forecasts are produced **recursively** — the model's own
prediction for week *t* becomes an input feature for week *t+1* — which is
why the confidence band widens with `sqrt(horizon)` (disclosed in the API's
`method_note` field, not hidden). The deployed model is **Linear
Regression**, selected over Random Forest, Naive Persistence and a
Moving-Average baseline — see "How accurate is your model?" below for why.

### "Why isn't this just a dashboard?"

A dashboard shows you numbers. This system combines a forecast with
deterministic vessel-port feasibility, a four-factor risk score, a priced
comparison of four concrete chartering scenarios, and a single traceable
recommendation with a numbered explanation — end to end, from one map
click. Removing any one layer breaks the product: forecast alone doesn't
tell you if the cheapest-looking vessel can physically dock; feasibility
alone doesn't tell you if now is a good time to book; cost alone doesn't
tell you *why*. See README §4 "Novelty" for the full positioning — we are
not claiming forecasting, AI, or GIS are individually novel.

### "How accurate is your model? / validation methodology?"

Chronological split (no shuffling): 1,248 weekly rows across 6 lanes → 70%
train / 15% validation / 15% test, split by calendar date, so no lane's
future ever appears in another lane's — or its own — training rows. Lag
and rolling features are computed with `shift(1)` **before** any rolling
window so no row's inputs can see its own target.

On the untouched test set (`ml/evaluation/results.json`, reproducible with
`python3 ml/evaluation/evaluate.py`):

| Model | MAE | RMSE | MAPE | Directional Accuracy |
|---|---|---|---|---|
| Naive Persistence | 0.693 | 1.017 | **3.66%** | 0.0% |
| Moving Average (4wk) | 0.890 | 1.226 | 4.63% | 53.3% |
| **Linear Regression (deployed)** | 0.697 | 1.015 | 3.76% | **61.7%** |
| Random Forest | 0.732 | 1.091 | 3.87% | 61.1% |

Naive Persistence has the best MAPE — expected, since weekly freight rates
behave close to a random walk — **but 0% directional accuracy**, because it
always predicts "no change." A model that can never signal direction cannot
power a BOOK NOW / WAIT decision, so `train.py` explicitly disqualifies any
candidate at or below a 50% directional coin-flip on the **validation**
set, then picks lowest MAPE among the survivors. This is a real, inspectable
methodological choice, not a cherry-picked result — rerun `train.py` and
the same rule applies to whatever data you feed it.

### "How did you avoid temporal leakage?"

Three separate guards: (1) chronological, not random, train/val/test split;
(2) every lag/rolling feature is built from `.shift(1)` before windowing,
so the feature for week *t* only ever sees weeks `< t`; (3) the reported
test metrics come from a **second, independent script**
(`ml/evaluation/evaluate.py`) that reloads the saved model artifact and
recomputes metrics from scratch — its output includes a `MATCH`/`DRIFT`
line diffing against the numbers `train.py` reported, so the claim is
mechanically checkable, not just asserted in this document.

### "Why was this vessel selected?"

`feasibility_service.evaluate_vessel()` checks cargo capacity, draft, LOA,
beam, and the port's compatible-class list for **every** vessel class,
always, and returns pass/fail + a human-readable reason for each check —
nothing is silently eliminated. The recommended vessel is the **cheapest
feasible** one (lowest `typical_daily_hire_usd`), not the biggest or the
first one checked. In the primary demo scenario (Coal, 80,000 t, Paradip),
Handysize/Supramax/Panamax are rejected on cargo capacity alone
(34k/56k/79k t < 80k t required) and Capesize is the only feasible class —
you can see this live in the Vessel Optimizer panel, not just read it here.

### "How do you know the vessel can operate at this port?"

We don't claim certified knowledge — the port dimensional limits are
`ESTIMATED` (general maritime knowledge, not an official port-authority
tariff book or IHO chart), disclosed as such everywhere they appear. What
we do guarantee is that the **comparison logic** is correct: given a
vessel's draft/LOA/beam/capacity and a port's limits, the feasibility
check is real arithmetic, always run, always shown. Swapping in verified
port-authority figures (the documented production replacement path) would
not require touching this logic at all.

### "What happens if the forecast is wrong?"

Three layers of protection against over-trusting a wrong forecast: (1) the
recommendation is never based on the forecast alone — it's cost + risk +
feasibility together, and a `HIGH` risk classification **overrides** a
cheaper-on-paper WAIT recommendation back to BOOK NOW (see
`recommendation_service.py`); (2) low model confidence (<55%) blocks a WAIT
recommendation entirely and returns MONITOR MARKET instead of committing to
an uncertain call; (3) every forecast ships a confidence interval that
widens with horizon, so the UI never presents a single point estimate as
certain.

### "What happens if data is missing?"

Never fabricated. Concretely: an unknown origin/cargo lane returns HTTP 422
with `data_status: "unavailable"` (tested:
`test_forecast_unknown_lane_returns_explicit_unavailable_not_fabricated_data`);
a missing model artifact makes the forecaster fall back to a disclosed
moving-average baseline (`data_status: "prototype-fallback"`, tested); a
port field that's genuinely absent renders literally as `DATA UNAVAILABLE`
in the UI, never a blank or a guessed number; any unhandled backend
exception returns a structured 500 with `data_status: "error"` rather than
leaking a stack trace or crashing the page.

### "How would this scale to production?"

The architecture is already structured for it: `ML_MODEL_PATH`/`DATA_PATH`
are swap points for a real dataset and a retrained model with zero
frontend changes; `DATABASE_URL` already switches between SQLite and
PostgreSQL; services are stateless functions over typed inputs, so they sit
behind FastAPI without change under horizontal scaling; the recursive
forecaster and feasibility/risk/cost services are all pure-computation, so
they cache and scale independently of the request layer. See README
"Production Roadmap" for the specific integrations (AIS, live congestion,
licensed freight index, ERP) still needed before real deployment.

### "How would real AIS/freight data be connected?"

`ml/ml_core/forecaster.py` reads `freight_rate_history.csv`-shaped data
through `DATA_PATH` — a production feed would write into the same shape
(date, origin_code, cargo_type, rate) from a licensed index subscription,
no forecaster code changes needed. Live AIS/congestion would replace the
static `congestion`/`risk` columns on the `ports` table with a scheduled
job writing current values from a VTMS/AIS provider — the risk engine
already reads those columns generically, so it would pick up live values
automatically once seeded from a different source.

### "Who uses the system?"

A chartering/procurement desk deciding when and on what vessel to move a
specific overseas bulk-cargo shipment to an East Coast port — the persona
implied directly by the problem statement (SAIL-style bulk cargo
procurement). Not a general logistics dashboard for arbitrary users.

### "How will you measure whether it actually works?"

We do not claim a savings percentage — no real deployment exists to
measure one from. What's implemented instead is the **methodology** to
measure it after deployment: `ml/evaluation/evaluate.py` already reports
MAE/RMSE/MAPE/directional accuracy against a held-out set on any dataset
dropped into `DATA_PATH`; post-deployment, the same script run against
real outcomes would report forecast accuracy, and comparing
`recommendation.action` outcomes against realized freight movement would
give a real (not synthetic) directional-accuracy and expected-vs-actual
cost-delta measurement — the scaffolding for that comparison already
exists in the `decision_runs` audit table.

### "How is this different from existing maritime intelligence solutions?"

We are not aware of, and do not claim to have researched, every commercial
maritime intelligence product, so we make no "we are the only ones who..."
claim. Our defensible, specific claim is narrower: **for this problem
statement's specific decision** (overseas-to-East-Coast-India bulk cargo
chartering), the combination of forecast + feasibility + risk + cost +
scenario comparison + explanation, running end-to-end from one map
interaction, in one demonstrable prototype, is what we built and can show
working — not a claim about the broader commercial market.
